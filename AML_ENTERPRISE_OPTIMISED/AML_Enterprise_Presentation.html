Advanced Matching & Scoring

RuleChain - Fuzzy Name Matching

Formula:
score = 0.30×token_sort + 0.30×token_set + 0.20×partial + 0.20×jaro_winkler

OWS-Aligned Three-Tier Scoring

1. Match Score

0.0–1.0
Name fuzzy matching quality

2. Risk Score

0–100
Watchlist record risk assessment

3. Priority Score

0–100
Alert queue prioritization
(60% match + 40% risk)

Multi-List Multiplier: When entity matches multiple watchlists, consolidated score increases by 15% per additional dataset (e.g., 3 datasets = 1.15² boost)

Policy Engine & Decision Making

Threshold-Based Logic with Review Band

REVIEW_BAND = ±0.08
if score ≥ threshold: → ALERT
else if |score - threshold| ≤ REVIEW_BAND: → REVIEW (manual analyst)
else: → NO_ALERT

Alert Severity Classification

CRITICAL
Score ≥ 0.92
HIGH
Score ≥ 0.80
MEDIUM/LOW
Score 0.65–0.80

Alert Routing: ALERT → ALERT_QUEUE (immediate) | REVIEW → REVIEW_QUEUE (analyst) | NO_ALERT → Logged only

LLM-Powered Negative News Screening

Solves Three Critical Problems

1
Entity Disambiguation
Distinguishes between different individuals with same name using context (company, country, role, age)
2
Severity Reclassification
Re-calibrates vendor coarse categorization (£500 fine vs. $50M fraud both marked FRAUD/0.70)
3
Relationship Extraction
Identifies linked entities for graph engine ("brother of sanctioned X")

Implementation Details

Parameter Value Purpose
Model Claude Sonnet 4 Latest LLM for reasoning
Activation Threshold name_score ≥ 0.40 Avoid unnecessary API calls
Confidence Floor entity_confirmed ≥ 0.30 Drop uncertain matches
Severity Blending 70% LLM + 30% Vendor Trust LLM calibration
Graceful Fallback: If LLM API fails, system continues with rule-based scores. Screening is never blocked by API failures.
