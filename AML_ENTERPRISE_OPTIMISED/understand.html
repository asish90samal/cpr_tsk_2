NEW config/rule_config.py 181 lines

Per-job rule enable/disable flags — OWS Run Profile equivalent

RuleConfig get_rule_config() list_all_configs()
WHAT IT CONTAINS

Defines a RuleConfig dataclass and a config dict for all 10 jobs. Controls which of the 8 atomic rules (I010O–I080O) are enabled per job. Phonetic is OFF for SAN/SCION, ON for PEP/NNS. DOB cluster OFF for all entity jobs.

WHY IT WAS NEEDED

OWS allows individual rules to be toggled on/off per screening type. Without this file, every job would run every rule — causing false positives (phonetic matching on strict sanction jobs) and wasted compute (DOB matching on entity jobs that carry no DOB).

NEW matching_engine/rules/atomic_rules.py 397 lines

8 discrete OWS-named atomic match rule functions

rule_I010O_exact() rule_I020O_fuzzy() rule_I030O_reversed() rule_I040O_given_family() rule_I050O_abbreviated() rule_I060O_phonetic() rule_I070O_transliteration() rule_I080O_dob_cluster() best_alias_score()
WHAT IT CONTAINS

Contains one pure function per OWS rule code. Each is independently callable, independently auditable. Also contains best_alias_score() which runs any atomic rule across primary name + all pipe-delimited aliases.

WHY IT WAS NEEDED

OWS reports show WHICH rule fired (e.g. 'matched on I050O Abbreviated given name'). The old code blended everything into one composite score — analysts couldn't see why a match was flagged. These functions make every match technique named, trackable, and individually tunable.

NEW matching_engine/rules/rule_chain.py 190 lines

Orchestrates atomic rules in priority order, returns best named result

RuleChain NameMatchResult
WHAT IT CONTAINS

RuleChain reads the per-job RuleConfig, runs only enabled atomic rules for a given candidate row, returns a NameMatchResult with the best-scoring rule's code + label + score + all_rule_scores dict.

WHY IT WAS NEEDED

This is the bridge between config and individual rules. Without it, each base_rule class would need to manually call every atomic function. RuleChain centralises orchestration so adding a new rule requires only adding it to atomic_rules.py and registering it here — nothing else changes.

NEW scoring/risk_element_weights.py 264 lines

OWS Appendix D risk element weighting table

get_weights() RISK_ELEMENT_WEIGHTS CATEGORY_RISK PEP_TIER_RISK DATASET_PREFIX_MAP
WHAT IT CONTAINS

Defines the per-list-type weighting table for 8 risk elements: res_ope_countries, nat_reg_countries, membership, category, occupation, deceased, active, external_risk. 13 list prefixes × 2 entity types. Also defines CATEGORY_RISK and PEP_TIER_RISK lookup dicts.

WHY IT WAS NEEDED

OWS produces a risk_score (0–100) separate from match_score. Without this table the system had no concept of 'how risky is this watchlist record' independent of how closely the name matched. An OFAC SDN record should score higher risk than a regional adverse media hit even at the same match score.

NEW scoring/risk_scorer.py 346 lines

Computes risk_score, priority_score, customer-side risk blend

score_record() compute_watchlist_risk() compute_customer_risk() compute_blended_risk_score() compute_priority_score() RiskScoringResult
WHAT IT CONTAINS

Implements OWS section 3.5 formula: wl_risk = Σ(element × weight), cust_risk from input record fields, blended_risk = (wl × 0.5) + (cust × 0.5) → 0–100 int. priority_score = (match × 0.6) + (risk/100 × 0.4) → 0–100 int.

WHY IT WAS NEEDED

OWS outputs 3 separate scores per alert: matchScore, riskScore, priorityScore. The old system had only rule_score which conflated match quality with risk level. Analysts need risk_score to understand record severity and priority_score to rank the alert queue.
